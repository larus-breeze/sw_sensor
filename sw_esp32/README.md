# ESP32 software

The ESP32 forwards NMEA data generated by the STM32 over UART, via WiFi TCP
and a second UART interface to the RS232 transceiver (`uart_bridge.cpp`),
and hosts a WiFi access point with a web UI for STM32 firmware updates,
`*.lrsx` flight log file management (`web_server.cpp`, `wlan_link_client.cpp`,
`ap_identity.cpp`, relayed to the STM32 over SPI2), and updating the ESP32's
own firmware (also via the web UI, written straight into the free OTA
partition, no STM32 involvement). See `documentation/wlan_link.md`
at the repository root for the full design and current implementation status.

The sketch is split across multiple files in `wlan_link/`
(Arduino compiles every `.ino`/`.cpp`/`.h` in the sketch folder together):
- `wlan_link.ino` — `setup()`/`loop()`, wires the pieces together
- `wlan_link_protocol.{h,cpp}` — wire format shared with the STM32 side
- `wlan_link_client.{h,cpp}` — SPI master driver talking to the STM32
- `ap_identity.{h,cpp}` — WiFi AP SSID/password derivation
- `wifi_config.{h,cpp}` — optional WiFi client mode (see below), with
  automatic fallback to the access point
- `web_server.{h,cpp}` — the update/log-file web UI (STM32 update, ESP32
  self-update, log file browser, SD card format, WiFi client mode config)
- `uart_bridge.{h,cpp}` — the UART/WiFi TCP bridge

## WiFi client mode

The web UI's "WiFi client mode" section can join an existing WiFi network
(SSID + password, persisted in NVS) instead of only running the sensor's
own access point. At boot, and again periodically in the background if
disconnected, the sensor tries to join that network; the access point stays
up throughout each attempt and is only actually handed over once a join
succeeds, so nothing already connected to it gets dropped by a failed or
in-progress retry. If the network can't be reached at all (or the
connection is later lost for more than a few seconds), the sensor falls
back to - or stays on - its own access point.

Once connected as a client, the web UI (and the NMEA TCP bridge, see the
Info table) move to whatever IP the joined network assigns - watch the
serial console at boot, or the joined network's router/DHCP lease list, to
find it. "Forget network" clears the saved credentials and returns to pure
access point mode after a reboot.

## Flashing the ESP32 firmware
- Flash the *.ino file with arduino studio via the esp32 usb connector
- Arduino IDE configuration
    - Select a **ESP32 Dev Module** board.
    - The Sensor uses a 8MByte ESP32 chip — set **Flash Size: 8MB (64Mb)**.
    - Set **Partition Scheme: Minimal SPIFFS (1.9MB APP with OTA/190KB
      SPIFFS)**. The compiled sketch (WiFi AP + web server + mbedTLS) needs
      more than the default "4MB with spiffs" scheme's 1.25 MB app
      partition gives ("text section exceeds available space in board").
      OTA updatability matters here, so this keeps the OTA_0/OTA_1
      partition pair rather than switching to a larger no-OTA scheme.

### Initial flash without a local toolchain (esptool-js)

For a first flash on a blank board, or a full reflash of an already-set-up
one, use Espressif's [esptool-js](https://espressif.github.io/esptool-js/)
in Chrome or Edge (uses Web Serial, no software install). Build first
(`python3 scripts/build_firmware.py`, see "Building a binary from the
command line" below) — this also merges the bootloader, partition table,
`boot_app0.bin` and application into two flat images in `build/` at the
repository root, at the offsets below. In esptool-js, click **Connect**,
select the port, add both files at their offsets, and click **Program**:

| Offset    | File                                          |
|-----------|-----------------------------------------------|
| `0x1000`  | `larus_sensor_esp32_v<version>.flash1_boot.bin` |
| `0xe000`  | `larus_sensor_esp32_v<version>.flash2_app.bin`  |

Deliberately two files, not one: the gap between them (`0x9000`-`0xe000`)
is the NVS partition — WiFi credentials, AP identity (`ap_identity.cpp`)
— and `esptool merge_bin` fills any gap it spans with `0xff`. Merging
straight across it would silently wipe NVS on every reflash, not just a
first one on a blank board; `build_firmware.py` stops the first image
right before it and starts the second right after, so it's never touched.

If a flash fails, confirm the offsets (the standard Arduino-ESP32 ones,
same regardless of partition scheme) via `arduino-cli compile
--verbose`'s printed `esptool` command instead of trusting them blindly.

## Updating the ESP32 firmware over WiFi

Once a board is already running this sketch, later updates don't need a USB
connection: connect to the device's WiFi AP, open its web UI (`192.168.4.1`
by default, or `http://larus.local` if the client OS supports mDNS), and
use the "ESP32 WiFi module update" section to upload a new
`larus_sensor_esp32_v<version>.bin` (from `scripts/build_firmware.py` - see
below - or the Arduino IDE's "Export compiled Binary", which instead names
it after the sketch). The ESP32 writes it into the free OTA
partition slot and reboots into it; the WiFi AP comes back up automatically
under the same SSID/password a few seconds later. A bad image here can't be
recovered over WiFi — fall back to a USB reflash per the section above.

## Python environment setup

`scripts/create-git-info-header.py` uses only the Python standard library.
`scripts/build_firmware.py` additionally needs `esptool` (to build the
merged flash images, see "Initial flash without a local toolchain"
above) and `arduino-cli` (a separate non-pip install - see below);
`scripts/generate_ap_label.py` needs a few packages of its own.
All of these are listed in `scripts/requirements.txt`. From `sw_esp32/`:

```
python3 -m venv .venv
source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r scripts/requirements.txt
```

`.venv/` is gitignored - recreate it any time with the commands above
rather than committing it.

## Building a binary from the command line
`scripts/build_firmware.py` builds the sketch headlessly with `arduino-cli`,
using the same board settings as the manual Arduino IDE flashing above
(ESP32 Dev Module, 8 MByte flash, Minimal SPIFFS partition scheme). It
requires `arduino-cli` with the `esp32:esp32` board core installed — the
script prints the exact install commands if that core is missing.

```
python3 scripts/build_firmware.py
```

This also (re)generates `wlan_link/git-commit-version.h`
(gitignored) with the current `git describe` output, shown as the ESP32
firmware version in the web UI's Info section. Building via the Arduino
IDE instead skips that step - run `scripts/create-git-info-header.py` by
hand first if you want an up-to-date version string in an IDE-built
binary; otherwise it falls back to a placeholder.

Three named images are copied to `build/` at the repository root (shared
with the STM32 side's `scripts/build_firmware.py`, so both firmware
images end up next to each other), all tagged with the same
`MAJOR.MINOR.PATCH-BUILD` from `git describe` (e.g. `0.7.6-157`) as the
STM32 side's own `larus_sensor_stm32_v<version>.bin` naming, close enough
to tell at a glance which pair of binaries belongs together:
- `larus_sensor_esp32_v<version>.bin` — the application image alone, for
  OTA updates or for re-flashing over an already-flashed board.
- `larus_sensor_esp32_v<version>.flash1_boot.bin` /
  `...flash2_app.bin` — bootloader + partition table, and
  `boot_app0.bin` + application, merged into two flat images at their
  correct offsets, for a from-scratch flash or full reflash (see
  "Initial flash without a local toolchain" above) — split in two so the
  NVS partition (WiFi credentials, AP identity) in the gap between them
  is never overwritten.

The raw arduino-cli build output stays in `sw_esp32/build/`
(gitignored, override with `--output-dir`):
`*.ino.bin`, `*.bootloader.bin`, `*.partitions.bin`,
`*.ino.flash1_boot.bin`, `*.ino.flash2_app.bin`, `*.elf`, `*.map`.

## Generating a printable WiFi-AP label

`scripts/generate_ap_label.py` renders a printable label (QR code + text)
for a device's WiFi AP SSID/password, so it can be scanned or read directly
off the device. It never recomputes the password itself — it only ever
renders the exact SSID/password the firmware already printed over serial at
boot (see `ap_identity.cpp`), either pasted in or read live from the serial
port, since guessing at the byte order `ESP.getEfuseMac()` uses could
silently produce a wrong-password label with no way to notice. The label
also prints the web UI's address (`--ip`, default `192.168.4.1`, the fixed
AP-mode address) as plain text next to the QR code — not part of the QR
payload itself, since the standard `WIFI:` QR format has no field for it.

With the venv from "Python environment setup" above activated:

```
# from values already read off the serial monitor:
python3 scripts/generate_ap_label.py --ssid Larus_1A2B --password ABCDEFGH23456789

# read them directly from a freshly flashed/reset board:
python3 scripts/generate_ap_label.py --serial-port /dev/ttyUSB0
```

Without `--output`, the label is written to
`build/larus_wifi_label_<ssid>.png` at the repository root (same `build/`
directory as the firmware images above) — the SSID is included in the
filename so labels for several devices don't overwrite each other.
